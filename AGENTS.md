# Portfolio repository instructions

## Bilingual content requirements

1. Every user-facing string must have both English and Simplified Chinese copy. This includes navigation, headings, body copy, buttons, form labels, placeholders, loading/error/empty states, dialog text, image `alt` text, and accessibility labels.
2. Do not add hard-coded user-facing copy directly to React components. Shared interface copy belongs in `app/translations.ts` and must use a stable semantic key.
3. Project content is addressed by stable semantic paths derived from project, article, and section IDs. Never use a complete English sentence as a translation key.
4. When adding or changing English content in `app/portfolio-data.ts`, update both `contentMessages.en` and `contentMessages.zh` in `app/translations.ts` in the same change. The English entry is intentionally checked against the source data so an existing translation cannot silently become stale.
5. Product names, project names, APIs, and established technical terms such as Unity, GitHub, OpenSpec, UGUI, and HLSL may intentionally remain in English. Register intentional exceptions in `scripts/check-i18n.mjs`; do not rely on an unreviewed fallback.
6. Before completing any content or UI change, run `npm run i18n:check`, `npm run lint`, and `npm run build`. Also switch languages in the affected page at least once when browser verification is available.
7. A missing Chinese translation is a defect even if the runtime safely falls back to English.

## Visual design system

New content must look as if it had always been part of the site. Reuse the system in `app/globals.css` and `app/portfolio.tsx`; `docs/portfolio-art-direction.md` records the reasoning and history.

1. Palette and surfaces: use the `:root` tokens: `--paper` page, `--surface` raised panels, `--ink` text, `--muted` secondary text, `--line` / `--line-strong` rules and borders, `--signal` (amber) for small text accents, focus and solid emphasis blocks, `--signal-soft` for amber fills and planes. `--signal-light` is for strokes, borders, separators and other decorative marks only; it is below 3:1 contrast on paper, so never use it for text that must be read. Tints are `color-mix()` of these tokens; the only other fixed colour for new work is the existing `#eeede6` diagram ground. Keep the fixed contour texture as the page background; text blocks over it get the `reading-surface` class (or join the existing reading-surface selector list) so contour lines never run through copy. Keep surfaces flat and square: no new gradients (the existing ones are only fade masks and hatch textures), no drop shadows (the paper-coloured `box-shadow` on `reading-surface` is a feathered mask, not a shadow), and no rounded corners beyond the existing tag pills (such as `.tag-list` and `.article-status`) and circular diagram nodes.
2. Typography: Geist (`--font-sans`) for headings and copy. Kickers, indices, metadata and tags use Geist Mono at 12px (10–11px only inside diagrams and tags); add them to the shared label rule that starts with `.brand-label, .brand small` (mono, uppercase, 0.08em tracking) instead of restyling them one by one. Number sequences with two-digit indices (01, 02, …), but only items of one kind that form an ordered set, such as chapters, projects, groups or disciplines. Never number unrelated actions or controls just for rhythm. Take sizes from the nearest existing component with the same role instead of inventing new ones: lead paragraphs 19–23px, reading copy 16–17px at 1.6–1.75 line height, card and row descriptions 14–16px in `--muted`. Never shrink headings, copy, bullet points or diagram labels to make a layout fit; widen or reflow the layout instead, and let long camel-case identifiers wrap between words with `breakableIdentifier` in `app/portfolio.tsx`. Chinese relies on the CJK fallbacks in `--font-sans` and the `:lang(zh)` rule that sets long paragraphs to 1.85 line height; add new long-form paragraph selectors to that rule.
3. Grid and spacing: containers are `min(1440px, calc(100% - 64px))`, `calc(100% - 48px)` at ≤960px and `calc(100% - 32px)` at ≤600px. New multi-column splits at ≥961px use the 12-column grid with 24px gutters (`repeat(12, minmax(0, 1fr))`, `column-gap: 24px`); inside an existing component, follow that component's own columns. Numbered rows use a 56px number column plus a 16px gap. Adding content must not move existing elements; align new blocks to the lines their neighbours already use instead of introducing new axes.
4. Home, archive and Other pages: add items through the existing components (`FeatureCard`, `ProjectPreview`, archive group headings, discipline rows, `SideProjectCard`) rather than new layouts. If a new section is unavoidable, build it from the same parts: a 2px ink rule on top, a two-digit index, a heading, then content on the grid.
5. Project detail pages: describe a project through data, not new markup. Add it to the right group in `projects` in `app/portfolio-data.ts` (two-digit `index`, `year`, 3–4 `tags`, `links`) and give it chapters with an `if (project.id === …)` block in `getBoardItems`. Each chapter has a title, a one-sentence `description` (rendered as the lead), then `details` or 3–6 `bullets`, optional `sources`, and at most one figure: `image`, `diagram`, `visual` (renders the project's own `gallery`, `image` or `visual` through `ProjectVisual`), or `pages` (the pages of a document, see Figures). Chapters render only when the project has `gallery`, `image` or `visual`, or when its id is added to the `hasBoardContent` check in `ProjectDetailContent`. The case page then builds the header, chapter index, sticky chapter bar and stacked chapters (number and title, full-width figure on an offset amber plate, then the copy) automatically. From 601px up the chapter bar keeps one row: a long chapter list narrows its number cells instead of wrapping, while the 12px numbers keep their size; on phones it may wrap to two rows. At ≥961px the copy is a Swiss lead-and-body split from column 3: the lead on the left, `details` on the right with the chapter's link and `sources` under them as a references list, and `bullets` across both columns in two columns; a chapter without `details` widens its lead and puts the references on the right. At ≤960px everything stacks in one 68ch column. Do not reintroduce side-by-side text and figure spreads or a side table of contents.
6. Figures: chapter images are WebP at least 1600px wide, because case figures display up to 1376px wide (game panels are 1600×731). Keep one aspect ratio within a project, keep text baked into an image legible at that size, and give every image translated alt text (`imageAlt`, or `alt` in a gallery). Declare each image's real pixel size (`imageWidth`/`imageHeight`, or `width`/`height` in a gallery); `tests/image-sizes.test.mjs` checks them against the WebP files, so run `npm test` after adding images. Images narrower than the figure display at their natural width, centred on the surface panel. Diagrams are HTML/CSS: add a `DiagramId` and a branch in `FlowDiagram` built from the existing vocabulary: a `flow-kicker` label, `--surface` nodes with `--line-strong` borders, one solid `--signal` core node and `--signal` arrows on the `#eeede6` ground. They must fit within 1040px, reflow at ≤600px so no label is clipped or broken mid-word, and take every label from `content("diagram.…")` keys in `app/translations.ts`. A diagram that also appears on a home card must fit the card at every width. A multi-page document such as a pitch PDF uses `pages`: one WebP per page, at least 1600px wide at the page's real ratio, each with translated `alt`, its real `width`/`height` (also checked by `tests/image-sizes.test.mjs`) and a short translated `label` taken from the document's own section names, not new numbers that could clash with the page's printed ones. The figure shows the pages as a row of small pages on the surface panel at ≥961px, the first page larger beside a 2×2 of the rest at ≤960px, and full width above that 2×2 at ≤600px; each page is a button that opens the image dialog. The layout is built for five pages (a cover and four more), so for a longer document show the five that carry it and leave the rest to the download. Pair it with a download: put the file in `public/documents/` and set the chapter's `href`, a `linkLabel` that states the file size, and `download: true`, which renders a same-origin download link marked ↓ instead of an external ↗ link.
7. Decoration: use only the site's existing devices: thin rules, two-digit indices, slanted amber planes (a `clip-path` polygon in `--signal-soft` at 0.42 opacity), the offset amber plate with a cut corner under case figures, and registration corners (`.profile-title-group::after`). Use at most one decorative device per component, and never let decoration cover content. Every device must serve the element it belongs to: lead the eye to it, mark it as clickable, or separate it. No free-floating decoration. Keep the container's left and right edges straight: shapes stay inside the margins, and the slanted `.details-action` cut is for small buttons inside cards, not for blocks that sit on the container edge.
8. Motion: reuse the existing one-shot keyframes (`headerReveal`, `strokeDraw`, `planeSlideIn`, `pageEnter`, …), never loop, and give every new animated selector a `prefers-reduced-motion: reduce` override.
9. Verification: in addition to the checks above, view the affected pages at 1440, 834, 390 and 320px in both languages. Nothing may be clipped or overflow horizontally, and on case pages the chapter bar must sit flush under the site header and keep one row from 601px up.
